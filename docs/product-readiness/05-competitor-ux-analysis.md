## 2. Strengths and weaknesses relevant to an internal replacement

| Product | Worth learning from | To avoid |
|---|---|---|
| Jira Cloud | Precise concepts (conditions, validators, post functions, schemes) that our admins already know; usage shown in admin lists; confirmations that state consequences. | Configuration spread across schemes and screens that ordinary project admins cannot follow. The full create modal is long. |
| monday.com | Plain-language automation; per-run automation log; people and teams found in one search. | A generic board model with weak workflow enforcement; a different mental model from Jira's for our users. |
| Linear | Speed and density: chip-based create, shortcuts shown everywhere, low chrome; import history. | Opinionated limits (fixed status categories, team-centric model) that may not fit the source configurations. |

## 3. Recommended UX model for Strand (original, traceable)

1. **Two administration layers:** project settings for project admins, and an Administration area for global admins (G08, G07, A12 backup setting).
2. **Concept names from Jira, simpler screens:** keep "transition", "condition" and "validator" as the help terms admins know, but use a three-tab transition panel instead of separate schemes (B03–B05).
3. **Every configuration change shows its impact before saving:** workflow, statuses, access widening, field option removal (B09, B10, G03, A10).
4. **Every automated or bulk change is attributable:** an actor in history, a run log, and a confirmation with a summary (H04, H09, C07).
5. **Dense and keyboard-first for daily work** (Linear), **explicit for administration** (Jira).
